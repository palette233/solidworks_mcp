# “自然语言需求 → 所需模组/文件”功能进展

> 更新时间：2026-09-10
> 当前定位：项目02可演示Demo；尚未形成跨项目、动态子集和文件级交付闭环。

## 1. 目标

使用者用自然语言描述设备功能或工艺需求，系统应当：

```text
自然语言需求
  → 识别工艺能力和显式否定
  → 补齐工艺依赖
  → 推荐必选/可选模组
  → 返回模组身份、文件位置及推荐理由
  → 人工确认
  → 按确认集合生成布局并进入CAD验证
```

当前短期目标是在项目02上验证“推荐结果正确、可解释、可确认”；长期目标是复用统一能力模型支持项目01、03、05、06，并把推荐结果直接转成可求解、可装配的文件集合。

## 2. 当前已实现能力

### 2.1 项目02模组知识库

| 模组 | 当前功能身份 | 当前返回的组件名 |
| --- | --- | --- |
| A100 | XYZ龙门与双阀点胶执行 | `FL9A24D062A100.001-1` |
| A180 | 条码扫描与追溯 | `FL9A24D062A180.001-1` |
| A200 | CCD视觉定位 | `FL9A24D062A200.001-1` |
| A300 | 排胶与废胶收集 | `FL9A24D062A300.001-1` |
| A500 | 胶阀/喷嘴校准 | `FL9A24D062A500.001-1` |
| A700 | 清洁与称重组合 | `FL9A24D062A700.001-1` |
| A800 | 产品传输与载具定位 | `FL9A24D062A800.001-1` |
| T401 | 胶水供应 | `T401AA-07388-0-1` |

当前知识库覆盖十类能力：点胶、传输、载具定位、扫码、CCD视觉定位、喷嘴校准、喷嘴清洁、胶量称重、排胶和供胶。

### 2.2 确定性需求解析

已经支持：

- 用中英文关键词识别上述十类能力；
- 提取“每个载具4个产品”等简单数量信息；
- 识别“不需要CCD”等显式否定；
- 当没有识别到支持的能力时返回缺失信息，而不是随意推荐；
- 输入相同则输出稳定一致，便于回归和审计。

当前不调用外部大模型。规则透明、可复现，但对复杂表达、同义词和上下文推断的覆盖有限。

### 2.3 能力依赖补齐

系统不是简单地把一个关键词映射为一个模组，而是先计算能力依赖闭包。例如：

- 点胶自动补齐产品传输、载具定位和供胶；
- 扫码自动补齐产品传输；
- CCD视觉定位自动补齐产品传输和载具定位；
- 校准、清洁、称重和排胶自动接入点胶主流程。

如果用户显式否定了其他需求必须依赖的能力，系统会保留该依赖并输出矛盾提示。

### 2.4 推荐、解释与人工确认

推荐结果包含：

- 识别到的显式能力及触发词；
- 由依赖规则补齐的能力及来源；
- 必选、可选和未选择模组；
- 每个模组的推荐理由；
- 能力覆盖率、假设和缺失信息；
- 当前固定布局求解器是否兼容该模组集合。

确认接口会再次检查必选模组、未知模组和当前求解器所缺模组，避免仅在前端勾选时绕过规则。

### 2.5 展示和数据留痕

展示页已经具备：

- 自然语言需求输入框；
- “解析需求并推荐”操作；
- 能力标签、依赖来源和覆盖统计；
- 模组卡片、必选/可选状态和理由；
- 人工勾选、确认及求解兼容性提示；
- 完整八模组确认后进入现有项目02布局求解。

最新推荐和确认会保存为JSON：

- `demo/requirements/project02_latest_recommendation.json`
- `demo/requirements/project02_confirmed_modules.json`

## 3. 当前实际闭环

目前真正走通的流程为：

```text
项目02自然语言需求
  → 规则识别能力
  → 依赖补齐
  → 推荐项目02模组编号和组件名
  → 人工确认
  → 若选择完整八模组，则进入现有项目02布局展示
```

示例输入：

```text
每个载具4个产品，需要双阀环氧胶点胶、扫码追溯、CCD视觉定位、
喷嘴校准、清洁、称重和排胶。
```

当前输出为10/10能力覆盖，并推荐A100、A180、A200、A300、A500、A700、A800和T401八类模组。

## 6. 尚未完成的关键能力

### 6.1 具体文件定位尚未闭环

当前推荐结果提供`module code + componentName`，但没有为每个模组返回经过存在性校验的完整`SLDASM/SLDPRT`文件路径，也没有处理同一能力对应多个候选文件、配置或实例的选择。因此当前更准确的名称是“需求到模组推荐”，还不是完整的“需求到可装配文件推荐”。

### 6.2 动态模组子集求解尚未实现

基础点胶需求可以正确推荐A100、A800和T401，但现有项目02布局求解器仍以完整八模组为固定输入。非完整子集可以被推荐和确认，却不会直接生成只包含该子集的布局或实体装配体。

### 6.3 仍然只支持项目02

项目01、03、05、06已有模组识别和案例参数，但尚未建立统一的“能力—项目实现模组—文件”注册表，也没有跨项目推荐API。

### 6.4 自然语言理解和澄清有限

- 依赖固定词典，尚不支持复杂长句、隐含功能和广泛同义表达；
- 缺少结构化多轮澄清，只能返回缺失信息；
- 冲突需求可以提示，但尚无人工裁决状态机；
- 产品数量尚未真正参与节拍、工位数量和产能选型。

### 6.5 工程选型与CAD验收未包含

当前推荐判断的是功能覆盖，不负责品牌型号、数量冗余、精度、节拍、维护性和采购选型。推荐模组集合也不等于布局合理或实体无干涉，仍需经过约束求解、人工选案、SolidWorks实体化、AABB/条件B-rep及保存重开验证。

## 7. 与现有项目主线的关系

目前已经积累的多项目模组识别、参数包、布局约束和配合图可以作为下一阶段的数据来源：

```text
多项目模组识别清单
        +
能力本体与依赖规则
        +
项目参数包/实际CAD文件索引
        ↓
统一“能力—模组—文件—配置—约束”注册表
```

但这些数据目前仍分散在项目专用代码和JSON中，没有由需求推荐引擎统一消费。

## 8. 建议的后续开发顺序

### 第一优先级：建立版本化模组/文件注册表

将当前Python常量迁移为可校验的JSON/YAML，至少记录：项目、模组代码、功能能力、完整文件路径、引用配置、实例数量、组合模组关系和证据来源。启动时检查文件存在、能力引用和依赖环，推荐结果直接返回可打开文件。

### 第二优先级：完成项目02动态子集求解

让确认后的模组集合真正决定：求解变量、工艺约束、碰撞对象对、展示对象和CAD物化输入。先验收三类固定场景：基础点胶、点胶＋扫码、完整八模组。

### 第三优先级：增加结构化澄清与冲突处理

对节拍、产品数、扫码、CCD、称重等缺失条件生成最少数量的澄清问题；冲突需求必须要求人工确认，不静默取舍。

### 第四优先级：迁移项目01、03、05、06

复用统一能力定义，每个项目只配置自身的实现模组、文件和布局参数；不复制项目02规则代码，不直接继承项目02坐标。

### 第五优先级：接入实体装配与分级干涉验证

只有唯一候选通过展示层人工确认后才生成SolidWorks装配体；先执行快速严格AABB，门洞/框架/嵌套关系再选择性执行叶级B-rep。

## 9. 当前结论

当前已实现一个可解释、可复现、可在网页演示的项目02“自然语言需求→模组推荐”Demo，并能在完整八模组场景下衔接布局展示。主要断点是：推荐结果尚未绑定完整CAD文件路径，确认的任意模组子集不能动态驱动求解，且尚未推广到项目01、03、05、06。

因此，下一阶段最有价值的工作不是继续扩充关键词，而是先建立统一模组/文件注册表并打通项目02动态子集求解，使“推荐哪些模组”真正决定“加载哪些文件、建立哪些约束、生成什么装配体”。
